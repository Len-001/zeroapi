# ZeroAPI 核心算法审查记录（四步协议）

> 本文按「状态与不变式提取 → 红蓝对抗 → 单步追踪 → 最小侵入修复」四步协议，
> 对原型中三个承担正确性责任的算法逐一审查。
> 所有行号对应交付时的工作副本；所有结论都有 `tests/` 下的可执行用例或
> `reports/verification.json` 里的实测数据支撑。

## 算法一：最小代价双射求解（匈牙利算法）

**位置**：`src/core/solver.js:56` `hungarian(cost, n)`

### 步骤 1 · 状态与不变式

| 类别 | 内容 |
| --- | --- |
| 循环不变式 | 主循环每轮为「行 `i`」找到一条增广路；`p[j]` 恒为当前已匹配到列 `j` 的行号（0 表示未匹配）；势能 `u/v` 始终保持**可行势**（`u[i] + v[j] ≤ cost[i][j]`） |
| 内层不变式 | `minv[j]` 恒等于"从已访问行集合到列 `j` 的最小松弛量"；`way[j]` 记录该松弛量的来源列 |
| 前置 P1 | `cost` 为 `n × n` 且**每个元素都是有限实数**（不得为 `NaN` / `Infinity`） |
| 前置 P2 | `n = 0` 时为合法输入 |
| 后置 Q1 | 返回 `assign`，`assign[i]` 为与第 `i` 行配对的列，且构成 `0..n-1` 的一个**排列** |
| 后置 Q2 | `Σ cost[i][assign[i]]` 在所有 `n!` 种排列中最小 |
| 后置 Q3 | 结果对输入顺序确定（严格 `<` 比较 + 列升序扫描） |

### 步骤 2 · 红蓝对抗（4 类反例）

| 编号 | 类别 | 用例 | 期望 |
| --- | --- | --- | --- |
| A1 | 最小边界 | `hungarian([], 0)` | 返回 `[]`，不抛错 |
| A2 | 最小边界 | `hungarian([[1,2]], 2)`（行数≠n） | 抛「cost 维度不匹配」 |
| A3 | 最小边界 | `hungarian([[1,2],[3,4],[5,6]], 3)`（行数=n 但行内长度≠n） | 抛「代价矩阵必须为方阵」 |
| B1 | 最大边界 | 12×12 全 1e9 量级代价 | 不产生 `Infinity`/`NaN`，选出对角 |
| B2 | 最大边界 | 128×128（见 `02-max-boundary.js`） | 双射合法，耗时归档 |
| C1 | 结构异常 | 输入行序颠倒 | 结果不变（Q3 确定性） |
| C2 | 结构异常 | 列序颠倒 | 配对结果集合不变 |
| D1 | 状态转移陷阱 | `cost[i][j] = NaN` | **立刻抛错**，绝不带着 NaN 静默产出错误匹配 |
| D2 | 状态转移陷阱 | `cost[i][j] = Infinity` | 立刻抛错（势能运算会产生 `Infinity - Infinity = NaN`） |
| D3 | 状态转移陷阱 | 增广失败（`j1 === -1`） | 抛错而非返回残缺排列 |

**覆盖**：`tests/cases/01-min-boundary.js`、`02-max-boundary.js`

### 步骤 3 · 单步追踪（最可能失败的一组：D2）

若不显式拒绝 `Infinity`，取 `n = 2`、`cost = [[0, Infinity], [1, 1]]`：

| 步 | `i0` | `j0` | `delta` | `j1` | `u` | `v` | 说明 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| ① | 1 | 0 | — | — | `[0,0,0]` | `[0,0,0]` | 进入 `i=1` 的增广 |
| ② | 1 | 0 | `0` | 1 | — | — | `minv[1]=0`，`minv[2]=Infinity`；`delta=0`，`j1=1` |
| ③ | — | 1 | — | — | `[0,0,0]` | `[0,0,0]` | `used[0]=true` → `u[p[0]]+=0`；`minv[2]-=0` 仍为 `Infinity` |
| ④ | `p[1]=0` | 1 | — | — | — | — | `p[j0]=0` → 退出 do-while，配成 `(1,1)` |
| ⑤ | — | — | — | — | — | — | `i=2`：`minv[2]` 初始 `Infinity`；`cost[2][2]-u[2]-v[2] = 1`，但 `minv[1]` 仍为 `Infinity` |
| ⑥ | — | — | — | — | — | — | 所有 `j` 都被 `used` 或 `minv[j]=Infinity` ⇒ `j1 === -1`，`delta=Infinity` |
| ⑦ | — | — | — | — | `Infinity` | `-Infinity` | **若继续执行**：`u[p[j]] += Infinity`、`v[j] -= Infinity` ⇒ 下一轮 `cur = Infinity - Infinity` = **NaN**，`minv` 被 NaN 污染，第 89 行 `if (minv[j] < delta)` 恒为 false ⇒ 在第 91 行 `j1 === -1` 才暴露 |

**断言失效点**：`src/core/solver.js:91`（`if (j1 === -1) throw ...`）—— 此时错误已经离现场很远，
错误信息只会说"数值退化"，排查成本极高。

### 步骤 4 · 最小侵入修复

```js
// src/core/solver.js:59-67 —— 在进入主循环之前就把违反 P1 的输入挡掉
for (let i = 0; i < n; i++) {
  for (let j = 0; j < n; j++) {
    const v = cost[i][j];
    if (typeof v !== 'number' || !Number.isFinite(v)) {
      throw new RangeError(`hungarian: cost[${i}][${j}] 非有限值 (${v})`);
    }
  }
}
```

- **修改原因**：把"数值退化"这一远程症状，提前暴露为"某个具体元素非法"这一本地症状。
- **复杂度变化**：时间 `O(n²)` → `O(n² + n²)`（常数项翻倍，量级不变）；空间不变。
  实测 128×128 场景总耗时 138.49ms，其中匈牙利算法本体仅 1.39ms —— 前置校验的开销可忽略。

## 算法二：同构代价模型与最优求解

**位置**：`src/core/solver.js:155` `solveIsomorphism()` + `pairCost()`

### 步骤 1 · 状态与不变式

| 类别 | 内容 |
| --- | --- |
| 前置 P1 | `sourceNodes` / `targetNodes` 中字段名非空且各自唯一 |
| 前置 P2 | 代价函数非负且**有限**（不可匹配用常量 `PAD = 10` 表示，而不是 `Infinity`） |
| 前置 P3 | `PAD` 必须严格大于任何可行匹配的代价 —— 否则"放弃匹配"会和"勉强匹配"竞争 |
| 后置 Q1 | `pairs` 构成**部分双射**：一个源字段不得对应两个目标字段，反之亦然 |
| 后置 Q2 | `|pairs| ≤ min(|A|, |B|)` |
| 后置 Q3 | 每条 `pair.ops` 都通过 `verifier` 的 L1/L2/L3 三层校验 |
| 后置 Q4 | 结果与输入排列无关 |
| 关键设计 | 低于相似度门槛的字段对**在进入矩阵前**就被抬升为 `PAD`，而不是"先求解再事后过滤"——后者会破坏 Q2 的最优性 |

### 步骤 2 · 红蓝对抗（4 类反例）

| 编号 | 类别 | 用例 | 期望 |
| --- | --- | --- | --- |
| A1 | 最小边界 | 空源码 × 空目标码 | 0 对，指标全 0 |
| A2 | 最小边界 | 空串字段名 | 不崩溃，落进 `unmappedFrom` |
| A3 | 最小边界 | 单元素同名 | 1 对，代价 0 |
| B1 | 最大边界 | 64×64 / 128×128 全可配对 | 恒等配对、双射合法、耗时归档 |
| B2 | 最大边界 | 96×128（非方阵补齐） | `pairs = 96`，无幽灵配对 |
| C1 | 结构异常 | 两个源字段都表示"价格"，目标只有一个 | **恰好匹配 1 个**，落选者显式进 `unmappedFrom` |
| C2 | 结构异常 | `SP_MC` 与 `sp_mc` 同名共存 | 不重复占用同一个目标字段 |
| C3 | 结构异常 | 诱饵字段 `goodsCode` vs `goodsName`（字面相似 0.550） | 拒绝匹配（未锚定时门槛 0.68） |
| C4 | 结构异常 | 语义完全对得上但 `object → number` 无算子链 | 以 `no-transform-path` 拒绝，**而不是**以语义门槛拒绝 |
| D1 | 状态转移陷阱 | 输入顺序颠倒/旋转 | 结果逐条相同，总代价一致 |

**覆盖**：`tests/cases/03-structural.js`

### 步骤 3 · 单步追踪（最可能失败的一组：C1）

`S = [jg_fen(price), dj_fen(price)]`，`T = [priceYuan(price)]`：

| 步 | 动作 | `raw` 矩阵 | `assign` | 说明 |
| --- | --- | --- | --- | --- |
| ① | 补零到 2×2 | `[[0.0, PAD], [0.0, PAD]]` | — | 两侧都锚定 price ⇒ 相似度 0.982，代价 ≈ 0 |
| ② | 匈牙利求解 | — | `[0, 1]` | 行 0→列 0，行 1→列 1（虚拟列） |
| ③ | 后置过滤 | — | — | 行 1 的列索引 `1 ≥ |T|=1` ⇒ 判为虚拟空配 |
| ④ | 结果 | — | — | `pairs = [jg_fen→priceYuan]`，`unmappedFrom = ['dj_fen']` |

**若换成贪心**：行 0 与行 1 都会各自去抢列 0，最终要么产生**非单射**（同一目标被写两次），
要么依赖遍历顺序随机决定谁胜出 —— 这正是 Q1 存在的意义。
第 226-235 行的单射自检会在结果被使用前抛错，属于"防御性断言"，正常路径下不会触发。

### 步骤 4 · 最小侵入修复

本算法在设计阶段就避开了两个已知陷阱，未做修复性改动：

1. **`PAD` 用有限值而非 `Infinity`** —— 直接规避了算法一的 D2 问题；
2. **门槛前置**（`pairCost` 内 `sim < floor` 直接返回 `PAD`）—— 保证后置过滤只是安全网，
   不承担最优性责任。

时间复杂度：`O(|A| · |B| · (寻路)) + O(n³)`，其中 `n = max(|A|, |B|)`。
`findPath` 加了记忆化（`src/core/operators.js:132`），把 `n²` 次重复寻路降为查表。

## 算法三：自愈桥接器状态机

**位置**：`src/core/bridge.js:280` `convert()` + `:124` `structMatch()`

这是整个原型里**唯一一个有状态、且会在生产中被高频调用**的算法，也是缺陷密度最高的地方。

### 步骤 1 · 状态与不变式

状态集合：`IDLE（无拓扑）/ MATCH（命中缓存）/ DRIFT（检出突变）/ REBUILD（重求解）/ REJECT（自愈失败）`

| 类别 | 内容 |
| --- | --- |
| 前置 P1 | `payload` 为普通对象（数组 / `null` / 标量属于另一条路径） |
| 前置 P2 | `targetAdt` 非空 |
| 不变式 I-A | 单次 `convert` 内 `rebuild()` 调用次数 ≤ `maxRebuildPerCall` |
| 不变式 I-B | 任意路径下**不抛异常**（可用性优先于正确性，但见 I-C） |
| 不变式 I-C | 无法自愈时必须返回 `degraded = true`，绝不静默返回错值 |
| 不变式 I-D | 结构一致时必须**完全跳过求解**（重建次数不随请求数增长） |
| 后置 Q1 | 返回值键集合 ⊇ 已匹配的目标字段；未匹配字段**不产出**（也不填 null） |
| 后置 Q2 | 发生结构偏离时，`drift` 列表随返回值一并上报 |

### 步骤 2 · 红蓝对抗（4 类反例）

| 编号 | 类别 | 用例 | 期望 |
| --- | --- | --- | --- |
| A1 | 最小边界 | `payload = {}` | 不崩溃，走重建 → 验证为空 → 降级 |
| A2 | 最小边界 | 非对象载荷 `null/[]/'abc'/42/true` | **短路直通**，且**不触发任何重建** |
| B1 | 最大边界 | 单位 cent↔yuan 交替 20 次 | 每次金额都正确，零降级 |
| B2 | 最大边界 | 4 行"部分小数部分整数"混合列 | 整轮只允许 1 次重建 |
| C1 | 结构异常 | 字段改名 `jg_fen→dj_fen` | 自愈后金额仍为 399.99 |
| C2 | 结构异常 | 改名到无意义名 `v1`（注释同时丢失） | **拒绝猜测**：产出缺省，绝不把"分"当"元"放行 |
| D1 | 状态转移陷阱 | 重建持续失败 | 迅速终止；重建只尝试 1 次；`reason = shape-memo-hit` |
| D2 | 状态转移陷阱 | 预算压到 1 | `reason = rebuild-budget-exhausted`，重建次数 ≤ 1 |
| D3 | 状态转移陷阱 | 任意预算 ∈ {1,2,3,5} | 重建次数 ≤ 预算（硬不变式 I-A） |
| D4 | 状态转移陷阱 | 有/无旧桥接器两种降级路径 | `usedStaleEntry` 标志必须如实反映 |
| D5 | 状态转移陷阱 | 多路由并发 | 拓扑状态互不污染 |

**覆盖**：`tests/cases/04-state-transition.js`

### 步骤 3 · 单步追踪（真实击穿的一组：B2 —— 混合小数/整数列）

**症状**：端到端自愈基准里，"8 轮结构突变"触发了 **21 次**重建（预期 ≤ 10）。

**现场**：价格列单位翻转后，4 行数据分别变成 `399.99 / 1299 / 2199 / 399.99`
（部分是小数、部分是整数），`src/core/bridge.js:124` 的 `structMatch` 逐行判定：

| 行 | 载荷值 | 单样本单位判定 | 已编译 `node.unit` | `drift`? | 重建计数 |
| --- | --- | --- | --- | --- | --- |
| 1 | `399.99` | `yuan`（非整数） | `cent`（旧拓扑） | ✔ | 1 |
| 2 | `1299` | `cent`（整数 + 名字说分） | `yuan`（刚重建） | ✔ | 2 |
| 3 | `2199` | `cent` | `cent`（被行 2 重建污染） | ✘（但结果已错） | 2 |
| 4 | `399.99` | `yuan` | `cent` | ✔ | 3 |

单次请求内即发生 2 次重建，且第 3 行拿到的还是**基于错误单位编译出来的桥接器**。
`src/core/bridge.js:156` 的 `inferFromSamples([payload])` 只喂了**一个**样本 —— 这是根因。

**中间修复（失败）**：改为 `[...window, payload]` 联合判定。只解决了 B2，
却打挂了 B1（振荡用例）：窗口里残留一个旧的小数值，导致"单位回切到分"永远检不出来。

**第二次尝试（成功）**：把"取证"和"确认"拆开 ——

- 用**当前载荷**取证（反应快，`bridge.js:156`）；
- 用**窗口量级**确认（抗噪，`bridge.js:160` → `magnitudeJump()`，定义在 `:462`）。

`magnitudeJump` 回答的是一个"数据本身答不了"的问题：新值 `39999` 到底代表
`39999 分` 还是 `39999 元`？单看这一个数无法区分；但和该字段近期量级一比就能区分
—— 相差 ≥1.5 个数量级（≈30 倍以上）时，就不是"业务正常波动"，而是"单位换了"。

### 步骤 4 · 最小侵入修复

修复共 4 处，全部是**局部替换，无接口变更**：

| # | 位置 | 修改 | 原因 |
| --- | --- | --- | --- |
| 1 | `bridge.js:280` 之后 | 新增非对象载荷短路分支 | 垃圾载荷不构成"契约突变"，不应触发 O(n³) 重建 |
| 2 | `bridge.js:156-166` | 单样本取证 + 量级确认 | 同时解决"横跳"与"反应迟钝"两个反向问题 |
| 3 | `bridge.js` 原 `unit-hint-conflict` | **删除**该漂移分支 | 见下 |
| 4 | `bridge.js:327/332` | 预算闸门提到形状备忘之前 | 让两道闸门在任意配置下都可独立生效 |

第 3 处是最有价值的一条：`node.anchor.unitHint('cent') ≠ node.unit('yuan')` 是一个
**对每个后续载荷恒为真、且重建永远无法修好**的条件（名字和注释还是老样子）。
一旦发生单位翻转，它就会永久抖动。正确语义是：「名字说分、数据说元」属于
**已裁决并固化进拓扑的事实**，不是"观测到的结构又变了"。

复杂度变化：
- 时间：`structMatch` 从 `O(k)` 变为 `O(k · S)`（`S` = 窗口大小，默认 6，常数级）；
  但**端到端总重建次数从 21 降到 7**（8 轮突变场景），实际吞吐是净提升。
- 空间：新增 `state.unitSuspect` / `state.lastSuspect` 两个标量；窗口不变。

**实测效果**（`reports/verification.json`）：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 8 轮结构突变触发的重建次数 | 21 | **7** |
| 自愈时延 p50 / p95 | — | 1.339ms / 1.913ms |
| 缓存命中请求 p50 / p95 | — | 1.0ms / 2.0ms |

## 附：审查过程中被测试台架自身制造的 3 个假象

按纪律"断言失败先怀疑台架"，以下三个失败最终都定位为**测试代码的错**，而非产品缺陷：

1. **风格矩阵用例全绿但没测到东西**：`renameKeys` 的映射方向与 `styleMap` 相反，
   4 种命名风格其实一次都没改名，7/7 是"原始 schema 本来就能匹配"的假阳性。
   → 修正：把方向约定固化为 `{原字段名 → 现字段名}`，并加断言校验改名确实发生。
2. **重建次数恒为 0**：用 `b.rebuild = () => ({ok:false})` 注入失败，
   把计数器一起绕过了。→ 修正：改为标志位注入。
3. **指标断言恒不成立**：`bridge.reset()` 只清路由不清指标，测出来的永远是
   "进程启动以来的累计值"。→ 修正：区分 `reset()` 与 `resetMetrics()`，
   并在端到端里一律测**增量**而非总量。

## 附：审查过程中发现的 3 个真实产品缺陷

| # | 缺陷 | 危害 | 修复 |
| --- | --- | --- | --- |
| 1 | `verifier` 的时间不变量只写了单向判定 | 反向桥接（ISO → Unix）被误判违规，时间字段被静默剔除 | 改为方向无关的双向判定 |
| 2 | 启动器的"健康检查"用 `POST /api/sync` | **自检会真的写业务数据**，启动即污染下游 CRM | 改为只读探针 `GET /api/products` |
| 3 | 写路径复用了老 ERP 的静态契约当"源侧声明" | 源 ADT 凭空多出 7 个字段，产物变成一串 `null`（安静但致命的错值） | 写路径不传 `staticSource`，源 ADT 完全由运行时对象推断 |
